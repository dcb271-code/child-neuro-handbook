# Child Neurology Handbook

A Next.js 14 static site serving a pediatric neurology reference handbook, plus five
interactive clinical calculators. **The content is used by physicians at the point of
care** — see [Working on clinical content](#working-on-clinical-content) before editing
anything with a number in it.

## Commands

```bash
npm run dev            # local dev server
npm run build          # production build (also the closest thing to a full validation)
npm run test           # vitest, watch mode
npm run test:run       # vitest, single run
npm run build-search   # regenerate search.json + topic/figure counts  ← after ANY content edit
npm run cleanup        # idempotent HTML tidy across all section files
npm run extract        # rebuild all sections from the source .docx files
```

There is no lint step and no CI beyond the call-schedule automation.

## Content model

Each of the 20 sections is a single JSON file, `src/data/<slug>.json`:

| Field | Meaning |
|---|---|
| `html` | The entire section body as one HTML string. Rendered with `dangerouslySetInnerHTML` into a `.doc-content` container (`components/SectionContent.tsx`). |
| `toc` | `{level, text, id}[]`. Each `id` must match a heading `id` in `html` — or be a registered widget id (below). |
| `tocCount`, `imageCount` | **Derived.** Display-only badges. Regenerated by `npm run build-search`. |

`src/data/index.json` lists the sections in site order with their icon, colour, and a
copy of the counts. `src/data/board-review.json` and `factoids.json` are separate data
sets with their own shapes (board-review is a top-level array, not an object). So are the
two quiz banks rendered by the shared runner — `rite-exams.json` and `peds-quizzes.json`
(see below).

### Derived files — never hand-edit

`npm run build-search` regenerates all of these from `html`:

- `src/data/search.json` **and** `public/search.json` — byte-identical copies. The app
  fetches the `public/` one; Fuse.js indexes it in `components/GlobalSearch.tsx`. One
  entry per heading (deeper than the TOC: epilepsy has 96 TOC entries but 122 headings),
  plus a section-intro entry where meaningful text precedes the first heading.
- `tocCount` / `imageCount` in every section file and in `index.json`.

`lib/content/__tests__/consistency.test.ts` fails the test suite if any of it drifts —
dead anchors, duplicate heading ids, stale counts, or the two `search.json` copies
diverging. If it fails after a content edit, run `npm run build-search`.

Counts are patched by targeted string replacement rather than re-serializing the JSON,
because `scripts/build-call-schedule.mjs` writes `neuro-on-call.json` pretty-printed and
a full rewrite would fight it on every automated run.

### Widgets

Five calculators are injected into section pages at render time. Their anchors live in the
section `toc` but have **no matching heading** in `html`, because the component renders its
own. The ids are registered once in `lib/content/widgets.ts`; `app/[section]/page.tsx` maps
them to components and the consistency tests treat them as valid anchors. Adding a
calculator means touching that registry, the component map, and the section's `toc`.

| Widget | Section | Logic |
|---|---|---|
| ASM withdrawal | epilepsy | `lib/asm-withdrawal/` |
| Seizure risk (first & febrile) | epilepsy | `lib/seizure-risk/` |
| SUDEP risk | epilepsy | `lib/sudep-risk/` |
| Neonatal HIE | neurocritical-care | `lib/hie/` |
| SE med ladder | neurocritical-care | `lib/se-ladder/` |

Each has pure logic in `calculator.ts` with real unit tests in `__tests__/`. Keep the
logic pure and test it there rather than in the component.

### Quiz banks and the shared runner

Three quiz experiences live under `/board-review`, and two of them share one runner:

| Bank | Data | Adapter | Benchmarks |
|---|---|---|---|
| Board review builder | `board-review.json` | own components | n/a (instant feedback) |
| RITE practice exams | `rite-exams.json` | `riteSets` / `riteLocator` | per-PGY, 3–5 |
| Pediatrics in-service | `peds-quizzes.json` | `pedsSets` / `pedsLocator` | **none** |

`components/quiz-runner/` drives the latter two. It knows nothing about either concrete
type — it works against `RunnerQuestion` / `RunnerSet` / `RunnerConfig` in
`lib/quiz-runner/types.ts`, and `lib/quiz-runner/adapters.ts` maps each bank onto them.
Adding a third bank means writing an adapter, not editing the runner.

The pediatrics quizzes are for the PGY1–2 pediatrics years: 4 × 50 questions, mixed 30%
neurology / 20% genetics-metabolism / 50% general pediatrics, from the **Nelson 17th ed.**
self-assessment sets. That edition is from 2004; the supplied explanations carry
current-practice notes where the original key has been superseded. **Preserve those notes
verbatim** — they are the mechanism keeping dated content safe to study from.

They deliberately carry **no passing mark**. The RITE benchmarks are for a different exam,
and no published mark exists for these, so the runner shows a score and nothing else.
Don't add one.

Regenerate with `node scripts/build-peds-quizzes.mjs`; the markdown source is kept at
`scripts/sources/peds-practice-quizzes.md`. It must stay out of `public/` — it contains
the answer key in plain text.

### Roster vs. test identities

`lib/roster.ts` holds two lists. `MEMBERS` is the real 17-resident roster and
drives Family Points team rosters, PGY standings, and entry validation — a name in
it appears on the leaderboard. `TEST_MEMBERS` (currently just `BrockTest`) is
selectable in the progress picker but deliberately outside that list.

The split is enforced by which lookup a caller uses: `memberByName` resolves
residents only and is what Family Points validates against, while
`identityByName` resolves both and is what progress tracking, the identity
picker, and the quiz runner use. Widening `memberByName` would let test entries
pass Family Points validation and then vanish for having no team. Test
identities sit at `TEST_PGY` (0), rendered as "Test" via `pgyLabel` and sorted
last via `comparePgy`, so they get their own progress group instead of skewing a
real cohort.

### Family Points

`/family-points` is a standalone dynamic page (like `/resources`, not a content
section): a team leaderboard for the residency's family competition. Roster, tasks,
and point values live in `lib/family-points/config.ts`; pure scoring logic and tests
in `lib/family-points/calculator.ts`. The entry log is a JSON blob in Vercel Blob
(`family-points/entries.json`), written through `app/api/family-points/entries/route.ts`,
which gates writes behind the same shared-password cookie as resources
(`lib/resources/auth.ts`). Team colors are the `.fp-c-{n}` classes in `globals.css` —
a CVD-validated categorical palette with separate dark-mode steps; color follows the
team, so don't reassign indexes.

## Working on clinical content

**Never silently change a drug name, dose, threshold, contraindication, or age cutoff.**
A confidently wrong number here is dangerous. The `/goal` command
(`.claude/commands/goal.md`) encodes the rule as two tiers: markup repair, typos, and
meaning-preserving rewrites may be applied directly; anything factual is *proposed* in a
report under `docs/goal-reports/` for the clinician to accept.

Two things that make this trap easy to fall into:

- **The same dose is often stated in several places** — the prose pathway table, a
  separate dosing-tables section, the on-call quick reference, and a calculator. They
  drift. Grep for the drug name across `src/data/` *and* `lib/` before changing anything,
  and propagate an accepted change to every location.
- **Conflicting values are frequently both defensible** — a guideline figure vs. an
  institutional pathway vs. product labeling. Do not "correct" toward the literature
  standard; surface the conflict and let the clinician choose. Decisions already settled
  are recorded in `docs/goal-reports/`.

Calculator dosing carries sourced citations (PMIDs) in the component's references tab;
the prose largely does not. When they disagree, the calculator has usually been audited
more recently — but confirm rather than assume.

## Call-schedule automation

`.github/workflows/auto-build-call-schedule.yml` runs `scripts/build-call-schedule.mjs`,
which ingests an XLSX and rewrites two things: `public/call-schedule/index.html`, and the
tail of `neuro-on-call.json`'s `html` from the `<section aria-label="On Call Resources">`
marker onward. **Anything after that marker will be overwritten**; content before it is
safe to edit by hand. This accounts for most of the recent commit history.

## Conventions

- Tailwind, with content styling driven by `.doc-content` rules in `app/globals.css`
  and `@tailwindcss/typography`. Match the HTML patterns already in the section files —
  semantic `h2/h3/h4`, tables wrapped in `.table-wrap` — rather than inventing new markup.
- Dark mode throughout; every new component needs `dark:` variants.
- Section pages are statically generated via `generateStaticParams`.
